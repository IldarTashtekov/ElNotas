Anatomía de ElNotas

Pieza a pieza por el andamiaje de la Fase 0 y el dominio puro de la Fase 1: qué hace cada fichero, por qué existe y qué pasaría si no estuviera.

La Fase 0 ya está commiteada. La Fase 1 está en el working tree esperando tu revisión: 16 ficheros, unas 1.900 líneas, de las que 660 son tests.

Las dos fases resuelven problemas distintos. La Fase 0 no escribe nada de la app: monta las restricciones dentro de las que se va a escribir. package.json campo imports

El alias que entienden los tres a la vez

El problema: quieres escribir import { Note } from "#core/index" desde cualquier módulo, en vez de "../../core/domain/Note". Y quieres que eso lo resuelvan tres herramientas distintas: TypeScript al typechequear, Node al ejecutar los tests, y el bundler al construir.

La vía tradicional es declararlo tres veces —paths en tsconfig, resolve.alias en webpack, y un plugin para el runner— y rezar para que no se desincronicen. La vía que usamos es una sola declaración estándar:

"imports": {
  "#core/*": {
    "compiled": "./tmp-test/core/*.js",
    "default":  "./src/core/*.ts"
  }
}

Tres cosas que conviene entender de aquí:

  • El # es obligatorio. No es estética: Node sólo reconoce como subpath import los especificadores que empiezan por almohadilla. Es lo que le distingue de un paquete de node_modules.
  • Las claves son condiciones. Cada consumidor resuelve la primera que reconoce. TypeScript y el bundler no saben qué es "compiled", así que caen en "default" y apuntan al .ts fuente. Node, cuando se le pasa --conditions=compiled, coge la primera y apunta al JS ya compilado.
  • Por eso los tests funcionan. Los tests corren sobre el JS de tmp-test/, pero en el código escriben el mismo #core/index que escribiría la UI. Sin la condición, el require("#core/index") del JS compilado apuntaría a un .ts que Node no sabe ejecutar.
Si añades un módulo

Cuando exista src/storage/, hay que añadir su entrada #storage/* aquí. Hasta entonces no está declarada a propósito, y eso da un efecto secundario útil: si el core intentase importar #ui/algo, falla con Cannot find module simplemente porque ese alias todavía no existe.

tsconfig.base.json + tres más

Por qué hacen falta cuatro tsconfig

La razón de fondo cabe en una frase: lib y types se aplican por invocación de tsc, no por fichero. En el momento en que decidiste que el core no viera el DOM pero la UI sí, quedó garantizado que harían falta al menos dos configuraciones. Las otras dos son economía (no repetir opciones) y los tests (que necesitan otro sistema de módulos).

Qué cubre y qué prohíbe cada uno

tsconfig.base.json No compila nada. Sólo opciones que heredan los otros tres. strict · noUncheckedIndexedAccess · ES2020
tsconfig.json La app. Todo src/ menos los tests. lib: ES2020 + DOM + DOM.Iterable
src/core/tsconfig.json Sólo src/core/, sin sus tests. La verja. lib: ES2020 · types: [] · sin DOM
tsconfig.test.json Todo src/, tests incluidos. Emite a tmp-test/. module: nodenext · types: ["node"]

Lo que hay en la base, y por qué

Dos opciones merecen comentario. noUncheckedIndexedAccess hace que indexar un Record devuelva T | undefined. Es fricción real —tienes que comprobar el caso en cada lookup— pero con un estado normalizado donde todo se busca por id, "ese id no existe" es exactamente el bug que no quieres descubrir en runtime.

Y lo que no hay: ni paths ni baseUrl. Lo primero porque el campo imports ya lo cubre. Lo segundo porque baseUrl está deprecado en TypeScript 6 y deja de funcionar en el 7 — TS ofrecía silenciarlo con ignoreDeprecations, pero eso sólo aplaza el problema.

src/core/tsconfig.json la pieza central de la Fase 0

La verja de pureza

Es lo que convierte «el core no depende de la plataforma» de una convención que se erosiona en un error de compilación. Son tres líneas:

"lib":   ["ES2020"],   // sin DOM  -> document, window, localStorage no existen
"types": [],           // sin @types/node -> tampoco process ni Buffer
"noEmit": true

Dentro del core, escribir document.getElementById(...) o crypto.randomUUID() no compila. No es un aviso ni una regla de estilo: npm run typecheck:core sale con error.

La consecuencia práctica es la que hace que la arquitectura funcione: si el core necesita un ID, la hora o azar, no le queda más remedio que recibirlos de fuera. De ahí que las acciones traigan meta: { now, rev } en la Fase 1 — no es una elección de estilo, es que la alternativa literalmente no compila.

Dos detalles de implementación

Los tests están excluidos ("exclude": ["**/*.test.ts"]). La pureza aplica al código de producción; un test sí puede usar node:test y APIs de plataforma.

Está dentro de src/core/ y se llama tsconfig.json, no tsconfig.core.json en la raíz. Eso es a propósito: tu editor busca el tsconfig.json más cercano al fichero abierto, así que al editar código del core te marca el error mientras escribes, y no sólo cuando lanzas el script.

Lo que la verja NO cubre

Que el core no importe de ui/ o storage/ hoy se sostiene porque esos alias aún no están declarados. Cuando existan, la verja seguirá pillando el caso real —la UI usa DOM, así que arrastrarla al core rompe el typecheck— pero el mensaje de error será menos claro que un limpio Cannot find module. Merece la pena tenerlo presente.

tsconfig.test.json + el script test

Tests sin instalar un runner

Node 20 trae node:test y node:assert/strict de serie. Lo que no trae es la capacidad de ejecutar TypeScript. De ahí que npm test haga dos cosas:

tsc -p tsconfig.test.json && node --conditions=compiled --test tmp-test

Primero compila todo src/ a tmp-test/, y luego lanza el runner sobre el JS resultante. El --conditions=compiled es la pieza que conecta esto con el campo imports: sin él, el JS compilado intentaría cargar ficheros .ts.

El tsconfig.test.json usa module: "nodenext" en lugar del ESNext de la app. La razón es práctica: como el package.json no declara "type": "module", ese ajuste emite CommonJS, y CommonJS resuelve imports relativos sin extensión. Con ESM habría que escribir ./schema.js en el código fuente TypeScript, que es la clase de peaje que no merece la pena pagar en los tests.

Lo que cuesta

No hay watch mode, y cada npm test compila antes de ejecutar, así que es más lento que un runner dedicado. Y queda un problema abierto: los adaptadores sobre FileSystemDirectoryHandle y OPFS de la Fase 3 necesitan un navegador real, y esto no lo cubre. Es la decisión a tomar cuando lleguemos ahí — puede que la respuesta sea instalar algo sólo para esa fase.

domain/Ids.ts 50 líneas

IDs que el compilador sabe distinguir

Con un estado normalizado, absolutamente todo se referencia por id — y todos los ids son string. Sin más, pasar un PlanId donde se espera un NoteId compila perfectamente y el fallo aparece en runtime como «esa nota no existe». La marca lo arregla:

declare const brand: unique symbol

type Branded<T, B extends string> = T & { readonly [brand]: B }

export type NoteId    = Branded<string, "NoteId">
export type PlanId    = Branded<string, "PlanId">
export type ContentId = Branded<string, "ContentId">

El truco es que brand es un unique symbol declarado pero nunca creado. La propiedad no existe en runtime; sólo vive en el sistema de tipos. Un NoteId es un string a todos los efectos prácticos, pero un string no es un NoteId. Coste en el bundle: cero.

Para cruzar la frontera están los constructores, que son los únicos sitios del proyecto donde se hace el cast:

export const noteId = (raw: string): NoteId => raw as NoteId

ItemRef: la decisión más importante del modelo

export type ItemRef =
  | { readonly kind: "note"; readonly id: NoteId }
  | { readonly kind: "plan"; readonly id: PlanId }

Un Contexto guarda esto, no las entidades. Tu modelo original tenía items: (Note | Plan)[], y cambiarlo tiene tres motivos independientes, cada uno suficiente por sí solo:

  1. Una nota puede estar en varios contextos. Con las entidades embebidas, cada nota vive dentro de un contexto y sólo uno — lo que hace imposible el ContextoCompuesto que describías en tus comentarios.
  2. Guardar un contexto no reescribe sus notas. Con las entidades dentro, cualquier adaptador de persistencia serio queda condenado a leer y escribir el árbol entero.
  3. Es discriminable en runtime. Note y Plan son ambos { id, name, ... }: dado un elemento de la lista, no hay forma fiable de saber cuál es. El campo kind lo resuelve.

domain/Content.ts 66 líneas

El contenido de una nota

Dos cambios respecto a tu Models.ts, ambos deliberados.

Unión discriminada, no interfaz base

Tenías interface Content { type: string } con Text y CheckBox heredando. El problema es type: string: con eso, el compilador no puede comprobar exhaustividad en un switch. Si mañana añades un tercer tipo de bloque —una imagen, un separador— nada te avisa de los sitios que hay que actualizar. Con la unión, sí:

export type Content = Text | CheckBox

Text también lleva id

Tu modelo sólo daba id a la nota. Hace falta en los bloques por dos razones concretas: para direccionar «este párrafo» al editarlo, y porque la UI de la Fase 4 reconcilia por data-id y necesita una clave estable por nodo.

En CheckBox el id además evita un bug clásico. La alternativa sería direccionar una casilla anidada por su ruta de índices —[0, 2, 1]— pero esa ruta deja de ser válida en cuanto insertas o borras un hermano por encima.

La asimetría del árbol

Note.content: ReadonlyArray<Content>
├── Text        ← en la raíz caben textos
├── CheckBox
│   └── children: ReadonlyArray<CheckBox>
│       ├── CheckBox   ← por debajo, sólo casillas

Esa asimetría viene de tu modelo (children: CheckBox[]) y la respeté. Tiene una consecuencia que se nota al leer contentTree.ts: hay caminos de código duplicados, uno para el nivel raíz y otro para los niveles anidados, porque los tipos de los arrays no son el mismo. Si algún día decides que un texto pueda colgar de una casilla, ese fichero se acorta bastante.

shared/immutable.ts 63 líneas · la pieza menos obvia

Preservar la identidad

Si sólo vas a leer un fichero con atención, que sea este, porque de él cuelga el rendimiento de toda la app.

El Store decide si re-renderizar comparando por referencia: next === current. Eso funciona a condición de que una operación que no cambia nada devuelva el mismo objeto, no una copia equivalente. Y aquí está el problema:

const a = [1, 2, 3]
a.map(x => x) === a   // false — map SIEMPRE crea array nuevo
a.filter(() => true) === a   // false — filter también

Es decir: escribir el dominio con map y filter tal cual —que es lo que pide la regla de inmutabilidad— desactiva silenciosamente la detección de cambios. La app funcionaría igual de bien, sólo que re-renderizando entera con cada pulsación. Y ningún test obvio fallaría.

De ahí los tres envoltorios:

FunciónDevuelve la entrada intacta si…
mapPreservingIdentityningún elemento cambió de referencia
filterPreservingIdentityno se descartó ninguno
mapRecordPreservingIdentityningún valor del Record cambió
 
export const mapPreservingIdentity = <T>(
  items: ReadonlyArray<T>,
  fn: (item: T, index: number) => T,
): ReadonlyArray<T> => {
  let changed = false
  const next = items.map((item, index) => {
    const mapped = fn(item, index)
    if (mapped !== item) changed = true
    return mapped
  })
  return changed ? next : items
}

Como la comprobación se propaga hacia arriba, el efecto es compartición estructural: al marcar una casilla en lo hondo del árbol, se recrea sólo la cadena de nodos desde esa casilla hasta la raíz. Todas las ramas laterales conservan su referencia original, y la UI podrá saltárselas comparando con ===.

Si tocas el dominio

Esta es la invariante más fácil de romper sin darse cuenta. Hay tests específicos (describe("compartición estructural")) que la vigilan; si añades una operación, añade también su test de identidad.

domain/contentTree.ts 355 líneas · 41 tests

Las operaciones recursivas

Aquí está la lógica de verdad de la Fase 1. Todas las funciones comparten un contrato:

  • Puras y totales. No lanzan excepciones nunca. Un reducer no puede permitirse petar.
  • Una operación que no aplica devuelve la entrada intacta, en lugar de fallar. Cada función documenta en qué casos concretos no hace nada.
  • Preservan la identidad, apoyándose en los helpers de arriba.

La guarda de move

Mover un nodo dentro de su propio subárbol es el bug clásico de los outliners: creas un ciclo y la rama entera desaparece del árbol. La comprobación es de una línea, pero hay que acordarse de ella:

if (isCheckBox(node) && findContent(node.children, target.referenceId)) {
  return content
}

indent y outdent no son operaciones nuevas

Están construidas sobre move, que es lo que evita duplicar la lógica de reinserción:

  • indent = mover dentro del hermano anterior.
  • outdent = mover detrás del padre.

Hay un test que comprueba que se deshacen mutuamente. Y una decisión de comportamiento anotada: al hacer outdent, los hermanos que quedan por debajo dentro del padre se quedan donde están — no los adopta. Algunos outliners hacen lo contrario; si prefieres ese comportamiento, es un cambio localizado.

Decisión que dejé abierta

Marcar una casilla padre NO arrastra a sus hijas. La primitiva es deliberadamente mínima. Si quieres cascada, es una decisión de producto que se compone en la UI llamando a setChecked sobre los descendientes — pero también puede argumentarse que debería ser el comportamiento por defecto del dominio. Es tuya.

Las entidades y el estado raíz

export interface AppState {
  readonly notes:    Readonly<Record<NoteId, Note>>
  readonly plans:    Readonly<Record<PlanId, Plan>>
  readonly contexts: Readonly<Record<ContextId, Context>>

Plano y normalizado, como una mini base de datos. Las entidades no se anidan unas dentro de otras: los Contextos guardan ItemRef.

Tres ausencias que son intencionadas:

  • El ContextoGeneral no está porque no es una entidad: es una vista derivada de notes y plans. Guardarlo sería duplicar datos que se pueden calcular.
  • Las Ventanas tampoco. La navegación es estado de vista, no de dominio. Mezclarlas aquí llenaría la persistencia de basura de UI y haría que abrir un menú marcara notas como sucias.
  • schemaVersion entra en la Fase 2, con el runner de migraciones que lo consume.

Todo es readonly y ReadonlyArray de arriba abajo. Eso convierte tu regla de «nunca push ni splice» en algo que el compilador hace cumplir en vez de depender de que te acuerdes.

De Plan sólo están los tipos. El editor de grafos sigue fuera de alcance, y no hay ni una operación sobre planes. Queda anotado que, si llega ese editor, probablemente nodes deba pasar de array a Record: las aristas se guardan por id y con un array toda búsqueda es lineal.

app/actions.ts 126 líneas

Por qué las acciones traen la hora

Cada acción mutante lleva esto:

export interface ActionMeta {
  readonly now: number   // ms epoch, del puerto Clock
  readonly rev: Rev      // revisión nueva
}

Parece verboso, y la alternativa —que el reducer llame a Date.now() y genere un uuid— parece más cómoda. Pero esa alternativa ni siquiera compila dentro del core, porque la verja de pureza le ha quitado el acceso a las dos cosas. Así que la restricción de la Fase 0 fuerza el diseño correcto de la Fase 1.

Y resulta que el diseño correcto tiene tres ventajas de propina:

  1. El reducer es una función pura de (estado, acción), así que los tests son deterministas sin simular ningún reloj. No hay fake timers en ningún sitio.
  2. Todas las entidades que toca una acción reciben exactamente la misma marca de tiempo, en vez de milisegundos ligeramente distintos.
  3. Quien construye las acciones es la capa de casos de uso, que sí tendrá Clock e IdGenerator inyectados. Eso llega en la Fase 2.

La unión cubre notas (create, rename, delete), su contenido (siete acciones, una por operación del árbol) y contextos (create, rename, delete, addItem, removeItem, setDefaultView). Ninguna de planes.

app/reducer.ts 257 líneas · 25 tests

Dos invariantes en todos los casos

1. Si no cambia nada, devuelve el mismo estado

El helper que lo concentra para todas las acciones de contenido:

const updateContent = (state, noteId, meta, transform) => {
  const note = state.notes[noteId]
  if (!note) return state
  const content = transform(note.content)
  if (content === note.content) return state   // ← aquí paga la identidad
  return withNote(state, { ...note, content, updatedAt: meta.now, rev: meta.rev })
}

Fíjate en lo que consigue esa línea: un indent imposible, o marcar lo que ya estaba marcado, no ensucia updatedAt ni rev. Sin ella, cada acción inocua marcaría la nota como modificada y dispararía una escritura a disco en la Fase 3. Hay tests que lo comprueban explícitamente.

2. Integridad referencial

No se deja una referencia apuntando a algo inexistente. En concreto:

  • Borrar una nota la quita también de todos los contextos que la listaban, y actualiza los metadatos de esos contextos (pero no los de contextos que no la tenían).
  • Añadir a un contexto una referencia a algo que no existe es un no-op.
  • Poner como vista por defecto una nota que no existe es un no-op — si no, abrir el contexto te dejaría una pantalla en blanco.
  • Borrar un contexto no borra sus notas: pueden estar en otros contextos.

El switch es exhaustivo por tipos

default: {
  const exhaustive: never = action
  void exhaustive
  return state
}

Si añades una acción a la unión y se te olvida manejarla, action deja de ser never en ese punto y el fichero no compila. En runtime devuelve el estado intacto, que es lo prudente si algún día llega una acción desconocida desde datos deserializados.

app/Store.ts 48 líneas · 6 tests

Donde todo lo anterior se cobra

Cuarenta y ocho líneas, sin dependencias y sin plataforma. La UI se suscribirá y despachará; la persistencia se enganchará como un suscriptor más, con write-behind y debounce.

Qué pasa en un dispatch

1Llega la acción. Se calcula next = reduce(current, action).
2Se compara next === current.
→ ≠Se guarda el estado nuevo y se notifica a los suscriptores.
→ ==Se sale sin avisar a nadie. Ni un re-render.

Esa segunda rama es el motivo de todo el cuidado con la identidad en immutable.ts, en contentTree.ts y en el reducer. Si cualquiera de esas capas devolviera siempre un objeto nuevo, la comparación sería siempre falsa y la optimización desaparecería en silencio — sin errores, sin tests rojos, sólo una app más lenta de lo que debería.

Un detalle pequeño pero real: al notificar se recorre una copia de la lista de suscriptores.

for (const listener of [...this.listeners]) listener(next)

Así un suscriptor puede darse de baja (o de alta) durante su propia notificación sin corromper la iteración. Hay un test que lo cubre, porque es el tipo de cosa que sólo falla en producción y de forma intermitente.

index.ts 61 líneas

La API pública del módulo

Todo lo que consuman ui/, storage/ o platform/ se importa de aquí, nunca apuntando a ficheros internos. Es lo que hace que el límite del módulo exista de verdad: si mañana mueves src/core/ a packages/core/, el resto del proyecto no se entera.

La regla complementaria: dentro del core los imports son relativos (./domain/Note), no por el alias. El alias es para cruzar fronteras, no para uso interno.

Deuda consciente

  • La asimetría raíz/anidado de contentTree.ts genera caminos de código duplicados. Se arreglaría permitiendo textos como hijos de casillas, pero eso se aparta de tu modelo.
  • Dos casts feos, ambos encerrados y comentados: uno en mapRecordPreservingIdentity (porque Object.keys devuelve string[] y nuestras claves son ids marcados) y otro en sameView del reducer (comparar un NoteId con un PlanId requiere bajar a string).
  • El prototipo de src/scripts/ no se puede construir hasta la Fase 4, porque webpack está desinstalado.

Lo que aún no existe

Nada de persistencia: no hay puertos, ni StorageAdapter, ni BlobStore. Nada de UI nueva. Ninguna operación sobre Planes. Y ningún caso de uso — la capa que inyectará Clock e IdGenerator para construir las acciones con su meta es justamente lo primero de la Fase 2.
